# AI Coding 心法

利用 AI 提高开发效率，同时把项目转化为自己的技术能力：能解释关键设计、独立修改核心功能，并在面试中用代码和测试证明自己的判断。

**AI 负责加速实现，你负责理解问题、做出取舍、验证结果。**

**推荐学习方式**：

1. 自己分析需求
2. AI 帮助设计与实现
3. 审查关键代码和测试
4. 自己复述并独立修改

> **低效学习方式**
>
> 1. 把需求全部交给 AI
> 2. AI 生成大量代码
> 3. 能运行就接受
> 4. 继续开发下一个功能

## 一、先规划方向，再逐个功能推进

项目开始时明确目标、约束和优先级，不必提前设计所有实现细节。

| 功能类别 | 示例 | 规划程度 |
| --- | --- | --- |
| MVP 必做 | 登录、商品管理、创建订单、库存扣减 | 明确需求和开发顺序 |
| 面试重点 | 并发控制、幂等、缓存优化 | 明确问题，方案通过实验确定 |
| 可选扩展 | 推荐系统、优惠券、复杂报表 | 记录想法，按需展开 |

可以先确定“需要支持高并发抢购”，再根据约束和测试决定是否引入 Redis、消息队列或分布式锁。

**整体规划 → 功能设计 → 按 Task 实现 → 验证与学习 → 调整后续计划。**

Task 按技术决策、模块边界和验证成本拆分，不按代码行数。每个 Task 应有明确结果、少量关键决策和可执行的验收标准。例如，将订单功能拆成创建订单、库存并发控制、支付状态、取消订单。

确认功能方案后，让 Codex 按 Task 推进；每个重要**功能完成后集中学习**，避免每写几行就停下来讲解。

## 二、把 AI 的方案变成自己的判断

即使方案和代码由 AI 提供，你仍需掌握四件事：**定义问题、明确约束、比较方案、验证选择。**

1. **先描述需求。** 例如：“聊天需要实时收发、断线后补发；当前单实例、用户量较小。”先说需求，不急着指定技术。
2. **补齐知识地图。** 不知道有哪些方案时，让 AI 解释候选技术分别解决什么问题、适用条件和局限，并指出当前项目可能不需要的复杂度。
3. **自己提出倾向。** 例如先选 WebSocket，暂不引入 Redis，因为当前没有跨实例分发需求。让 AI 反驳你的假设、指出失败场景。
4. **用实验修正判断。** 通过压测、并发测试或故障复现，判断方案是否满足需求。

学习应逐渐从“AI 给方案，我解释”过渡到“我先设计，AI 评审”。

### 示例：库存扣减

需求是“多个用户购买同一件商品时不能超卖”。先复现“查询库存后再扣减”的并发问题，再比较原子条件更新、悲观锁、乐观锁等方案。理解事务、Redis、消息队列各自解决的问题，避免把它们当成同一层次的替代品。

可以对比有缺陷的实现与条件更新版本，用并发测试验证多个请求竞争最后一件商品时，最多只有一个请求成功扣减。随后独立扩展为“一次购买多件”，再考虑重复提交与重试带来的幂等问题。

**防超卖、订单与库存的事务一致性、重复下单是不同问题，需要分别验证。**

### 重要决策留下简短记录

低影响且容易修改的细节交给 AI，快速审查；

API、缓存策略等需要自己判断；

数据模型、认证架构、服务拆分等高影响决策应深入比较，并记录 ADR。

```text
问题：如何实现聊天消息传输？
约束：单实例、用户量小、需要双向实时通信。
候选：轮询、WebSocket、WebSocket + Redis Pub/Sub。
选择：WebSocket，暂不引入 Redis。
理由：满足当前需求，无需跨实例分发。
风险：重连、持久化、离线补发仍需处理。
验证：记录实际测试结果，未验证项单独列出。
调整条件：多实例部署时重新评估消息分发。
```

每个主要功能重点研究 1–2 个有价值的决策，比给所有细节补一套理由更有效。

## 三、按链路和机制学习，跟上项目增长

不必逐行重读 AI 生成的代码。先建立项目地图，再深入关键链路。

| 层次 | 学习重点 | 达成标准 |
| --- | --- | --- |
| 项目全景 | 业务目标、模块职责、依赖和数据存储 | 不看文档画出架构 |
| 核心链路 | 选 3–5 条业务流程，追踪入口到存储 | 两分钟讲清一条链路 |
| 关键机制 | 并发、事务、缓存、幂等、异步与可靠性 | 解释取舍、预测失败场景 |
| 独立实践 | 定位代码、修改功能、运行测试、排查故障 | 完成一个未看过答案的小需求 |

例如阅读秒杀下单代码时，沿着下面的链路追踪，并以实际实现为准：

```text
Controller → 限流 → Service → 消息队列 → Consumer → 数据库
```

重点问：在哪里校验资格？事务在哪里开始和结束？响应成功代表请求已接收，还是订单已创建？消息重复、消费者失败时会发生什么？

按技术价值分配精力：

- **样板代码、DTO、普通配置：** 知道用途，快速检查。
- **业务协调和模块调用：** 能解释输入、输出、数据流与异常路径。
- **并发、事务、幂等、安全等核心机制：** 能解释为什么这样写、去掉关键逻辑会怎样，并独立修改和测试。

同一技术主题集中记录，不要在每个 Task 中重复学习事务或幂等。每个主要功能只挑 1–2 个陌生且重要的主题深入研究。

### 不熟悉框架时，增加一条基础学习主线

按知识依赖学习框架，结合岗位要求查漏补缺，不完全跟随项目代码出现的顺序。

**遇到机制 → 学最小原理 → 预测实验结果 → 独立运行 → 回到项目应用。**

例如不理解 Spring Boot 事务时，先在最小项目中独立实现 Controller、Service、Repository 和回滚测试，再分析真实订单功能的事务边界、代理机制与失效场景。

理解注解用途只是起点；能独立使用、解释原理并排查失效原因，才算逐步掌握。

## 四、用独立实践和证据检验能力

每个重要功能最后留一个“独立扩展挑战”。从 AI 示范，过渡到只给提示，再到自己完成需求分析、代码定位、设计、实现、测试和排错。

可选择三类练习：

- 普通业务：商品筛选与分页。
- 事务业务：订单取消与库存恢复。
- 并发或异步：重复请求保护、重复消息处理。

每周安排一次**脱离 AI 的训练**：自己画架构、追踪核心链路、完成小修改，或定位一个可复现的 Bug。求助时先要方向提示，再要代码位置，最后才看局部示例。

- 能画出项目架构和核心数据流 不看AI 解释, 自己画图并口头说明 
- 能解释关键技术选型 至少比较一种替代方案 
- 能独立修改一个核心功能 关闭AI, 自己编码, 运行和调试 
- 能定位一个真实或模拟 Bug 使用日志, 断点, 测试找到原因 
- 能回答项目相关的面试追问 不看笔记, 连续讲解 5-10分钟

如果能连续独立完成 2–3 个不同类型的陌生需求，并解释相关机制，才更有依据判断自己具备独立开发能力。

### 面试亮点来自工程过程

**为什么做这个项目 → 遇到了什么技术问题 → 比较了哪些方案 → 最终如何实现 → 如何验证结果 → 还有哪些可以改进。**

使用 Redis、MQ 等通用技术也能体现个人能力，关键是讲清楚：

**背景 → 约束 → 候选方案 → 选择理由 → 实现与验证 → 局限和改进。**

例如秒杀系统可以逐步对比：

| 版本 | 验证重点 |
| --- | --- |
| 同步下单 + 数据库 | 数据竞争、吞吐和正确性 |
| 增加限流 | 拒绝率、延迟与数据库负载 |
| 增加队列与异步下单 | 积压、最终成功率、端到端延迟和故障恢复 |

如果限流后已经满足目标，保留简单方案同样是有价值的决策。引入队列后，则要解释重复消费、失败补偿和结果查询等新问题。

30 秒 **项目概览**：项目解决什么问题、主要技术栈、你的核心工作

2 分钟 **架构与关键链路** ：整体架构、重要模块、一次完整业务流程

5–10 分钟 **技术深挖** ：设计取舍、关键代码、失败场景、测试结果和优化依据

面试中不是要求你把整个项目一次讲完，而是能够根据追问，从项目全景快速切换到某条链路、某个技术专题，甚至某段关键代码。

优化方向：

1. **发现通用方案在当前项目中的不足**：⭐

   > 最初选择了“限流 + 消息队列”。
   >
   > 但进一步思考会发现：
   >
   > - 请求进入队列，不代表用户一定能购买成功。
   > - 队列积压过多，用户可能等待很久。
   > - 消息重复消费，可能导致重复创建订单。
   > - 消费者处理失败，可能导致订单丢失或库存状态不一致。
   >
   > 这些问题不需要发明新技术，但需要你设计解决机制

2. **据项目约束做出不同于通用教程的取舍**

3. **实验结果证明技术决策**

4. **主动识别系统的边界 ** ⭐

   > 高级一点的面试官通常更关注：
   >
   > “如果你的系统流量扩大 10 倍，会发生什么？”
   >
   > “如果消费者宕机，队列中的订单怎么办？”
   >
   > “如果 Redis 中的库存和 MySQL 不一致，如何处理？”
   >
   > 你不需要在项目中实现所有复杂机制，但要知道**当前方案能保证什么、不能保证什么**，以及**下一步应该如何改进**。



## 五、文档只记录值得复习的内容

```sh
docs/
├── project-plan.md       # 目标、MVP、优先级和开发顺序
├── architecture.md       # 实际架构、模块和关键链路
├── decisions/            # 重要决策、替代方案与验证
    ├── 001-order.md
    └── 002-inventory.md
└── learning/
    ├── 01-project-map.md  # 是否理解整个项目
    ├── 02-core-flows.md   # 能否讲清楚核心业务流程
    ├── topics/           # 技术专题，避免重复讲解
    │   ├── concurrency.md
    │   ├── transactions.md
    │   ├── idempotency.md
    │   └── messaging.md
    ├── learning-map.md   # 掌握状态与实际证据
    ├── exercises.md      # 独立练习与调试记录
    └── interview.md      # 追问、自己的回答和知识盲点
```

功能笔记只保留：目标、调用链与代码位置、关键机制、设计取舍、实际测试结果、一个独立练习和几个面试追问。只有独立解释或完成实践后，才更新掌握状态。

最终能够：

- 不看代码, 能画出项目整体架构 
- 能讲清楚3 条核心业务链路 
- 能深入解释 3 个重要技术机制 
- 能独立定位并修改一个核心模块 
- 能解释项目中至少2个技术设计取舍 
- 能回答项目相关的连续面试追问

## 六、可复用 Prompt

### project-plan

```
请作为我的软件架构导师，帮助我规划一个用于技术面试展示的项目。先分析我的目标岗位、技术水平、项目需求和时间预算。

请协助我：
1. 定义项目目标和核心业务场景。
2. 将功能分为 MVP 必做、面试重点、可选扩展。
3. 识别需要提前确定的基础架构和数据模型。
4. 标记可以延后决定的技术方案。
5. 给出功能依赖关系和建议开发顺序。
6. 对每个面试重点功能提出值得研究的技术问题。
7. 将结果整理为 docs/project-plan.md。

不要一次性设计所有功能的实现细节，也不要直接开始编码。请明确区分项目事实、假设和待验证的问题，并让我参与关键优先级决策。
```

### 规划与设计

```text
请先阅读项目，不要修改代码。我的目标是：[功能或项目目标]。
1. 区分代码确认的事实、假设和待验证问题，补齐关键约束。
2. 项目规划时区分 MVP、面试重点和可选扩展；当前功能比较 2–3 个方案。
3. 让我先提出倾向，再质疑我的假设、失败场景和取舍。
4. 提出成本最低的验证实验。
5. 将确认的方案拆成可独立验证的 Task，列出依赖、风险和验收标准。
不要提前设计所有功能，也不要替我编造选择理由。
```



```
架构导师 我正在开发一个用于求职面试展示的项目。

请先阅读项目代码，不要修改文件。

针对我准备实现的功能：
1. 解释业务需求与核心技术问题。
2. 给出 2–3 种实现方案及优缺点。
3. 推荐适合当前项目的方案。
4. 列出需要修改的文件和关键函数。
5. 告诉我面试官可能追问的技术问题。

```

### 知识储备不足导致无法独立设计

```
请先阅读当前项目中与库存扣减相关的代码、数据库结构和事务配置，不要修改文件。

我目前不了解库存并发控制的技术方案。请不要直接推荐最优方案，而是先帮我建立技术认知地图。

要求：
1. 用当前项目中的代码解释库存超卖是如何发生的。
2. 介绍从简单到复杂的常见解决方案，包括原理、适用条件、限制和依赖。
3. 区分数据库事务、原子条件更新、悲观锁、乐观锁、Redis、消息队列各自解决的问题。
4. 给出方案之间的关系，避免把不同层次的技术混为一谈。
5. 指出哪些方案对当前项目可能过度设计。
6. 标明哪些判断来自现有代码，哪些只是推测。
7. 最后给我三个理解检查问题，不要直接替我做选择。
```

### 实现与学习

```text
按已确认的 Task 依次实现，Task 内自主修改、测试和修复。
出现重大架构调整、重要依赖、破坏性操作或关键需求歧义时暂停沟通。
每个 Task 完成后，简要说明行为变化、关键文件、设计决策和实际测试结果。

请根据当前项目维护 docs/learning-map.md。
每个重要功能完成后：
1. 从真实请求追踪调用链，标出事务、异步边界和失败路径。
2. 只选 1–2 个重要且陌生的机制深入讲解，关联实际代码。
3. 给出最小实验，先让我预测结果，再验证。
4. 留一个独立修改练习，先给提示，不直接给答案。
不要逐行讲解样板代码，也不要把成功生成代码视为我已掌握。
```



```
编程搭档 现在按照已确认的设计实现功能。

请遵守以下规则：
- 一次只实现一个可以验证的小步骤。
- 每一步说明修改了哪些文件，以及为什么。
- 对关键算法、数据结构和设计决策进行解释。
- 添加必要的测试并运行。
- 每一步完成后暂停，等待我检查。
- 不要为了省事引入不必要的依赖。
- 遇到复杂问题先让我尝试分析，再给出解决方案
```

```
5. 标出事务边界、异步边界、异常处理位置；
6. 给出正常流程和一个失败流程；
7. 区分代码中已经实现的机制与尚未处理的风险。最后让我尝试独立复述整个流程。
```

```
技术导师

```



### 核心机制

```
请找出当前 Task 中最重要的三个技术机制。
对每个机制：
1. 指出对应的真实代码位置；
2. 解释它解决的具体问题；
3. 给出一个最小可运行示例；
4. 设计一个删除或修改关键逻辑后会出错的反例；
5. 向我提出一个预测结果的问题；
6. 等我回答后再运行实验并解释结果。不要直接告诉我答案，也不要把普通样板代码当成重点。
```

```
请基于当前 Task 的真实代码，生成 docs/learning/task-xxx.md。
要求：
用不超过200字概括功能；
列出核心调用链及文件位置；
选出1–3个重要技术机制；
```

## TDD 测试驱动开发

[SKILL](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)

- 红色: 开发新功能或修复bug之前, 先写一个测试用例, 这个测使用例是失败的 
- 绿色: 用**最小化**的代码修改让上述测试通过 
- 蓝色: 在绿色保障的基础上, 更优雅的重构或者优化上述最小化的代码, 并且还要一直保证测试是通过的



坏的测试: 耦合了「实现细节」, 是 TDD的反面教材.。 

- 它们盯着内部数据结构, 私有方法, 内部调用次数; 

- 一旦你重构 cart.py ，哪怕对外行为完全没变, 它们就会无理由地变红;

- 它们「证明」的是代码长什么样, 而不是代码能做什么.

好的测试用例，只测试对外暴漏的东西。不要测试函数里面的实现细节。
